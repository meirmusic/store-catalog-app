# שיטת העבודה: Decision Driven Design (DDD)

*סטנדרט הפיתוח מ-21/10/2026 (החלטת מאיר: "אני רוצה שזה יהיה סטנדרט הפיתוח שלנו מעכשיו"). SPEC.md סעיף 31.*

**הרעיון:** לפני שבונים - מדמים את ההחלטות. דמויות שמשתמשות באפליקציה מתווכחות, הטענות נבדקות
**על האפליקציה האמיתית** (מדידות, הדמיות), ומאיר מקבל רשימת החלטות ברורה: "החלטנו X, כי Y" - עם איור
"נדחה מול נבחר" לכל החלטה שרואים. מאיר מאשר לפי מספרים.

## כמה DDD - לפי גודל השינוי

| גודל | דוגמה | מה עושים |
|------|------|------|
| **תיקון תקלה** | REG-053 | שורת "החלטנו X, כי Y" ב-TEST_PLAN + בדיקה שנכשלת בלי התיקון. בלי ויכוח. |
| **שינוי קטן** | טקסט, צבע, כפתור אחד | בדיקה קצרה מול הדמויות (מי נפגע?) + החלטה אחת עם איור |
| **תכונה / עיצוב / ארכיטקטורה** | חבילה ב', לופ השיפור | **מלא**: דמויות ← ויכוח ← עץ ← סימולציה מדודה ← החלטות + איורים |

## השלבים (מלא)

1. **דמויות** - הצוות הקבוע (למטה) + מי שהתכונה נוגעת בו.
2. **ויכוח** - 3-6 סבבים קצרים; כל טענה שאפשר לבדוק - מסומנת לבדיקה.
3. **עץ החלטות** - כל צומת: האפשרויות, ✕ / ✓.
4. **סימולציה** - על האפליקציה האמיתית: מדידות (גובה, זמן, גודל, כמה נחתך), הדמיה בטלפון ובמחשב, בהיר
   וכהה, ותרחישי "מה אם" (שני מכשירים, בלי אינטרנט, רקע). **מספר שלא נמדד - כתוב שהוא הערכה.**
5. **החלטות** - "החלטנו X, כי Y", ממוספרות. מה שעלה בסימולציה ולא היה בבקשה המקורית - מסומן ⚠️ חדש.
6. **איור לכל החלטה שרואים** - 1200×600: כותרת של 4-6 מילים, משמאל הנבחר (מסגרת ירוקה ✓), מימין הנדחה
   (מסגרת אדומה מקווקוות ✕), בכל צד: צילום אמיתי מהאפליקציה, שורה טכנית אחת, ותוצאה ב-2-4 מילים. גופן 20+.
7. **אישור** - "מאשר 1-5, בלי 6". ואז: אפיון ב-SPEC ← בנייה ← בדיקות (התהליך הרגיל, CLAUDE.md).

כל מסמך נשמר ב-`docs/ddd/NNN-name.md`, האיורים ב-`docs/ddd/NNN-name/`.
